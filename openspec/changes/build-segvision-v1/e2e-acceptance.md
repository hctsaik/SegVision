# SegVision v1 E2E 驗收標準

> 規格狀態：Normative acceptance contract  
> 適用 change：`build-segvision-v1`  
> 機器清單：`acceptance/e2e-cases.json`  
> 門檻：`acceptance/acceptance-profile.json`  
> 證據格式：`acceptance/evidence.schema.json`

## 1. 驗收原則

SegVision v1 不以「GUI 能開」、「模型能回 mask」或「大部分測試通過」作為完成標準。Release candidate 必須逐案通過本文件的 mandatory scenarios，並產生可重跑、可追溯、可驗 hash 的 evidence bundle。

驗收分三層：

| Tier | 目的 | 是否可由 AI Agent 完成 | Release 意義 |
|---|---|---:|---|
| A | deterministic core / GUI / fault injection | 是 | 必須通過 |
| B | 固定 MobileSAM、reference CPU、offline package | 是，有合法模型與指定機器時 | `engineering-accepted` 必須通過 |
| C | 代表性真實場景、獨立 gold、人類操作 | Agent 可執行分析但不可偽造資料或人 | `domain-validated` 必須通過 |

規則：

- Mandatory functional scenarios pass rate 必須為 `100%`。
- Required scenario 不得 skip、xfail 或以「環境問題」改算 pass。
- 同一 case 自動 rerun 後才綠燈仍算 flaky failure；修正根因後重新建立全新 run。
- Screenshot 只作鑑識，主要 oracle 必須是 state、call ledger、mask/hash、schema 或 metric。
- Shared CI 不負責 reference-machine wall-clock gate。
- Tier C 輸入不足時，engineering-target 可保留 `engineering-accepted`；domain-target 必須使用 `BLOCKED_EXTERNAL_INPUT`，不得假造 `domain-validated`。

## 2. 必要測試設施

實作下列 deterministic doubles；沒有它們不得以人工點 GUI 代替自動驗收：

### 2.1 `ScriptedBackend`

必須可設定：

- 0～N masks、provider scores、stability、opaque previous state；
- encode / decode 延遲 barrier；
- timeout、exception、cancel acknowledgement；
- box / point / mask-prompt 回傳；
- encode / decode / release call ledger；
- 每次 decode 接收的 box、points、previous state 和 `multimask_count`。

### 2.2 `ScriptedCvExecutor`

必須固定回 `off`、`invalid`、`coarse` 或 `direct`，記錄 recipe hash、輸入 crop hash、輸出 mask hash與 call count。

### 2.3 `ControlledClock`

必須可精確前進到 `29_999`、`30_000`、`30_001 ms`，不得使用真實 sleep 驗證計時邊界。

### 2.4 `FaultInjectingAnnotationAdapter`

必須能在下列 checkpoint 注入失敗：

1. PNG temp write；
2. sidecar temp write；
3. temp verify；
4. PNG publish；
5. sidecar publish；
6. loader hash validation。

### 2.5 `GuiDriver`

必須透過真實 Qt mouse / key events 操作 widget，不得直接呼叫 controller method 冒充 GUI E2E。

### 2.6 Fixtures

至少提供：

- 1 px、奇偶尺寸、四邊 ROI、含洞、斷開元件、crop 截斷等 synthetic images/masks；
- 0、1、2、3、5 candidates；
- duplicate、near-full、point-violating masks；
- safe intersection 有／無的 candidate sets；
- valid/invalid/coarse/direct recipes；
- accepted、review、orphan、corrupt persistence pairs；
- 固定 MobileSAM checkpoint 的 model regression fixtures；
- 路徑含空格與中文的 package fixtures。

## 3. 每次 run 的證據

```text
evidence/<run-id>/
  run-manifest.json
  scenario-results.json
  junit.xml
  session-events.jsonl
  backend-calls.jsonl
  cv-calls.jsonl
  gui-states.jsonl
  filesystem-events.jsonl
  performance.json
  quality-report.json
  release-verdict.json
  cases/<case-id>/
    oracle-results.json
    ...case-specific ledgers and artifacts...
  commands/
  screenshots/
  outputs/
```

`run-manifest.json` 至少包含：

- source revision、dirty file hashes、OpenSpec change hash；
- OS、CPU、RAM、Python、dependency lock hash；
- backend/model/checkpoint/preprocess hashes；
- recipe hashes；
- fixture manifest hash；
- executed command、start/end、exit code、stdout/stderr hash；
- retry history；
- all produced artifact SHA-256。

## 4. Executable E2E case catalog

This catalog and `acceptance/e2e-cases.json` are co-normative. Every case ID appears exactly once, and implementers must not infer or substitute its pytest node, preconditions, steps, actor provenance, scenario links, oracles, or evidence.

The semantic validator MUST enforce globally unique case IDs and pytest nodes, exact parent `requirement_refs` for every `scenario_refs` set, valid stable references, exact reciprocal links with `traceability.json`, and fail-closed actor provenance. Only real annotators plus independent reviewers can satisfy Tier C human evidence; `scripted_test` never can.

### Cross-file hashing and execution rules

- `specs_sha256` MUST be computed by sorting `specs/*/spec.md` by POSIX relative path and, for each file, concatenating `relative_path + "\n" + UTF-8 file bytes`; SHA-256 is taken over the complete concatenation.

- A mandatory case with missing steps, missing oracle evidence, mismatched hashes, skipped/xfail status, or an unreported retry fails non-zero.
## 5. Threshold profile

機器門檻以 `acceptance/acceptance-profile.json` 為準。核心原則：

- mandatory Tier A/B cases：`100%` pass；
- accepted/review storage integrity violations：`0`；
- stale overwrite：`0`；
- wrong Accept：`0`；
- overlay/brush p95：嚴格 `<100 ms`；
- cached refine p95：target `≤1,000 ms`，miss 必須報告；
- scripted supported scenarios：valid Accept/Review decision 嚴格 `<30,000 ms`；
- Tier C：至少 100 張代表性 images、30 張 independent gold、90 張 valid accepted、30 張 independently reviewed accepted；valid Accept rate `≥0.90`、accepted-conditional `<30s` rate `1.0`、all-presented `<30s` Accept rate `≥0.90`、Needs Review rate `≤0.10`、timeout rate `0`、unresolved rate `0`、median boundary F1 `≥0.95`、每張 boundary F1 `≥0.90`、training-usable rate `1.0`、wrong Accept rate `0`。

任何 threshold 變更（即使更嚴格）都必須建立新的 versioned profile、對應 schema 與 OpenSpec change，並以新 hash 完整重跑；同一 run 不得變更。

## 7. Verdict

`release-verdict.json` 只能是：

```text
PASS_ENGINEERING
PASS_DOMAIN_VALIDATED
FAIL
BLOCKED_EXTERNAL_INPUT
BLOCKED_LICENSE
BLOCKED_REFERENCE_HARDWARE
```

Verdict、分類與專案狀態是三個不同欄位，並依 `acceptance/release-verdict.schema.json` 驗證：

- `target_release_class`: `engineering` 或 `domain`；
- `engineering_accepted` / `domain_validated`: 累積分類，後者為 true 時前者必須為 true；
- `project_state`: `in_progress`、`complete`、`implementation_complete_release_blocked` 或 `failed`。

若 target 是 engineering，Tier C 缺失不構成 blocker。若 target 是 domain、Tier A/B 已通過而 Tier C 外部輸入缺失，保留 `engineering_accepted=true`，verdict 為 `BLOCKED_EXTERNAL_INPUT`，project state 為 `implementation_complete_release_blocked`。

### `PASS_ENGINEERING`

- OpenSpec strict validation 通過；
- 所有 mandatory Tier A/B cases 通過；
- reference CPU 與 offline package evidence 完整；
- approved model/dependency manifest 沒有 blocking entry；
- Tier C 未通過時明確 `domain_validated=false`。

### `PASS_DOMAIN_VALIDATED`

- 先滿足 `PASS_ENGINEERING`；
- Tier C dataset/gold/reviewer evidence 真實且完整；
- 所有 domain thresholds 通過；
- required release/legal approval references 存在。

### 禁止 verdict

不得以 `PARTIAL_PASS`、`PASS_WITH_SKIPS`、`MOSTLY_PASS` 或重新執行直到綠燈的方式規避失敗。
